\section*{บทคัดย่อ}
ระบบจัดตารางสอบ เป็นระบบที่รับข้อมูลรายวิชา กฎการจัดสอบ และข้อมูลห้องจากแฟ้มต้นทาง แล้วแปลงเป็นรายการสอบเพื่อค้นหาวันและเวลาที่สอดคล้องกับข้อกำหนด รายงานนี้อธิบายแบบจำลองและลำดับการประมวลผลด้วยชื่อฟังก์ชันที่ตรวจสอบได้ โดยแยกข้อบังคับออกจากเกณฑ์ที่ใช้ปรับปรุงคุณภาพตาราง

รายงานทดสอบระบบด้วยชุดข้อมูลสังเคราะห์ที่สร้างซ้ำได้สามขนาด คือ 41, 100 และ 189 วิชา ครอบคลุม 8 สถานการณ์ที่กำหนดผลคาดหมายไว้ล่วงหน้า ทั้งกรณีใช้งานปกติและกรณีผิดพลาด การทดสอบเรียกโปรแกรมผ่านบรรทัดคำสั่ง ตรวจผลซ้ำด้วยเครื่องมือตรวจยืนยันที่แยกจากกระบวนการค้นหา และบันทึกภาพหน้าจอส่วนติดต่อผู้ใช้เป็นหลักฐานประกอบ

ในชุดข้อมูลหลัก ระบบกำหนดวันเวลาให้รายการสอบที่รับผิดชอบครบ 82 จาก 82 รายการ และสถานการณ์ทดสอบทั้งแปดให้ผลตรงกับที่กำหนดไว้ล่วงหน้า การค้นหาพิสูจน์ได้ว่าจำนวนรายการที่จัดได้ถึงขอบเขตบนที่คำนวณได้ในทั้งสามขนาด ส่วนจำนวนรายการในวันที่ควรหลีกเลี่ยงพิสูจน์ว่าต่ำที่สุดได้ในชุดเล็กและชุดกลาง เวลาทำงานครบกระบวนการผ่าน CLI มีค่ามัธยฐานประมาณ 0.56, 0.99 และ 2.12 วินาทีตามลำดับขนาด และการทดสอบความอ่อนไหวของพารามิเตอร์ของฟังก์ชันต้นทุนไม่พบความไวสูงของความครอบคลุมภายในช่วงค่าที่ทดลอง

ผลทั้งหมดได้จากข้อมูลสังเคราะห์ที่เลือกเงื่อนไขให้จัดครบได้ จึงไม่ใช่ตัวอย่างแบบไม่มีอคติของความยากทั้งหมด ผลด้านเวลาใช้ได้เฉพาะภายใต้สภาพแวดล้อมที่บันทึกไว้ และขอบเขตของข้อสรุปทั้งหมดสรุปไว้เป็นตารางการยืนยันในบทที่ 1

\subsection{ปัญหาและวัตถุประสงค์}
การจัดตารางสอบต้องประสานข้อมูลที่มีหน่วยและความหมายต่างกัน รายวิชาหนึ่งอาจมีหลายตอนเรียน นักศึกษากลุ่มเดียวกันอาจเรียนหลายวิชา และบางรายวิชามีวันเวลาสอบระบุมาแล้ว การย้ายรายการใดรายการหนึ่งจึงอาจกระทบรายการอื่น แม้ตารางที่มองเห็นจะมีช่องว่างอยู่ก็ตาม ปัญหาสำคัญไม่ใช่เพียงการหาช่องว่าง แต่เป็นการยืนยันว่าช่องนั้นใช้ได้ภายใต้ข้อมูลและกฎทั้งหมดที่เกี่ยวข้อง

รายงานนี้มีวัตถุประสงค์สามประการ ประการแรก อธิบายแบบจำลองและลำดับการประมวลผลด้วยชื่อฟังก์ชันที่ตรวจสอบได้ ประการที่สอง แสดงตัวอย่างที่ทำงานได้จริงทั้งกรณีปกติและกรณีผิดพลาด ประการที่สาม กำหนดขอบเขตของผลการทดสอบให้ชัดเจน โดยไม่ใช้การค้นหาไม่สำเร็จเป็นหลักฐานว่าปัญหาไม่มีคำตอบ
\subsection{หน่วยของข้อมูล}
คำว่า รายวิชา หมายถึงระเบียนที่ระบุด้วยรหัสวิชา ส่วน ตอนเรียน เป็นข้อมูลย่อยที่เก็บกลุ่มนักศึกษาและรายละเอียดจากต้นทาง รายการสอบ ผูกกับรายวิชาและประเภทการสอบ ได้แก่กลางภาคหรือปลายภาค จำนวนตอนเรียนจึงไม่ใช่จำนวนรายการสอบโดยตรง รายวิชา 41 วิชาในชุดหลักให้รายการสอบที่ระบบรับผิดชอบ 82 รายการ

รายวิชาที่มีบทบาท \code{managed} อยู่ในขอบเขตที่ระบบจัดตาราง ส่วน \code{context} ให้ข้อมูลประกอบ โดยเฉพาะรายการที่มีวันเวลาแล้วและอาจชนกับกลุ่มนักศึกษาเดียวกัน การไม่นับรายวิชาประกอบเป็นผลงานที่ระบบจัดใหม่ช่วยให้ตัวเลขความครอบคลุมไม่สูงเกินจริง
\subsection{อัตลักษณ์ของซอฟต์แวร์และการทำซ้ำ}\label{ch:identity}
ซอฟต์แวร์ที่ศึกษาคือ ระบบจัดตารางสอบ แพ็กเกจ \code{exam-scheduler-core} รุ่น 0.1.0 เผยแพร่ที่ \code{https://github.com/ItsBreadTime/examscheduler} ภายใต้สัญญาอนุญาต MIT การอ้างอิงสถานะโปรแกรมใช้ Git revision ของ repository ร่วมกับ snapshot ที่บันทึกโดยเครื่องมือ \code{docs/repro/snapshot.ts} ซึ่งเก็บแฮชของทุกแฟ้มที่อยู่นอก \code{docs/} การเปรียบเทียบก่อนและหลังการทำรายงานจึงตรวจได้ว่าโค้ดที่หลักฐานอ้างถึงไม่ถูกเปลี่ยนระหว่างการทำรายงาน โดยมีข้อยกเว้นที่บันทึกไว้เฉพาะบันทึกการทำงานชั่วคราวของเครื่องมืออัตโนมัติ หัวข้อในรายงานที่อ้างอิงแฟ้ม implementation รวบรวมไว้ในภาคผนวก \ref{app:trace}

รายงานนี้ใช้สถานะซอฟต์แวร์สองจุดเป็นหลักฐานอ้างอิง หลักฐานการทำงานผ่านบรรทัดคำสั่งและการวัดเวลาสร้างใหม่ที่ revision ปัจจุบันเมื่อวันที่ 6 กันยายน 2569 ส่วนภาพหน้าจอของส่วนติดต่อผู้ใช้บันทึกไว้ตั้งแต่จุดอ้างอิงเดิมของวันที่ 5 กันยายน 2569 ซึ่งต่อมาถูกบันทึกเข้าประวัติของ repository แล้ว การเปรียบเทียบแฮชรายแฟ้มระหว่างสองจุดอ้างอิงยืนยันว่าโค้ดของกระบวนการจัดตารางทั้งหมดภายใต้ \code{src/lib} ไม่ต่างกันแม้แต่ไบต์เดียว สิ่งที่เปลี่ยนคือแฟ้มระดับส่วนติดต่อผู้ใช้และการเผยแพร่ ซึ่งไม่มีผลต่อผลลัพธ์การจัดตารางที่รายงานอ้างอิง

รายงานฉบับนี้เพิ่มจุดอ้างอิงที่สามสำหรับชั้น cloud คือการตรวจระบบที่เผยแพร่จริงที่ \code{https://schedule.breadtm.xyz/} เมื่อวันที่ 6 กันยายน 2569 แฟ้ม JavaScript CSS และนโยบายความปลอดภัยของเนื้อหาที่เซิร์ฟเวอร์จริงตอบกลับตรงกับผลการสร้างใหม่จาก revision ปัจจุบันทุกแฟ้ม ผลการตรวจอยู่ในแฟ้ม \code{docs/data/cloud-verification.json} และรายละเอียดการบันทึกภาพหน้าจออยู่ในแฟ้ม \code{docs/screenshots/cloud-screenshots.json} ข้ออ้างเกี่ยวกับระบบที่เผยแพร่จึงอ้างถึงโค้ดชุดเดียวกับหลักฐานอื่นของรายงาน

การประมวลผลเริ่มจาก manifest ซึ่งบอกตำแหน่งแฟ้ม บทบาทข้อมูล และการตั้งเวลา เส้นทางแฟ้มใน manifest อ้างอิงจากโฟลเดอร์ที่เก็บ manifest จึงย้ายชุดข้อมูลทั้งโฟลเดอร์ได้โดยไม่ต้องแก้ตำแหน่งแบบสัมบูรณ์ ขั้นนำเข้ารวมระเบียนเป็นโครงการและตรวจปัญหาก่อนค้นหา ผลการตรวจขั้นนี้ต้องอ่านแยกจากผลตรวจหลังจัดตาราง

\code{importProject} รวมข้อมูล ตรวจแหล่งซ้ำและบทบาทที่ขัดกัน แล้วสร้างรายการสอบผ่าน \code{buildEvents} หากวิชาเดียวกันปรากฏทั้งในข้อมูล managed และ context ระบบรายงาน \code{SOURCE_ROLE_CONFLICT} แทนที่จะเลือกบทบาทใดบทบาทหนึ่งโดยไม่แจ้งผู้ใช้ การแยกบทบาทมีผลทั้งต่อจำนวนรายการที่ต้องจัดและต่อการคิดภาระการสอบ

\subsection{การแทนวันเวลา}\label{ch:time}
\code{ExamTiming} เก็บวันปฏิทินแบบ ISO ร่วมกับนาทีเริ่มและสิ้นสุดภายในวัน ไม่เก็บ instant หรือ timezone offset ค่านาทีเป็นจำนวนเต็ม โดยเริ่มตั้งแต่ 0 สิ้นสุดไม่เกิน 1440 และเริ่มน้อยกว่าสิ้นสุด การทดลองกำหนด timezone เป็น Asia/Bangkok เพื่อให้สภาพแวดล้อมสม่ำเสมอ ส่วนการคำนวณวันในสัปดาห์ใช้ UTC จากวันปฏิทินเพื่อหลีกเลี่ยงการเลื่อนวันตามเขตเวลาของเครื่อง

ฟังก์ชัน \code{overlaps} ตรวจว่าจุดเริ่มที่มากที่สุดน้อยกว่าจุดสิ้นสุดที่น้อยที่สุดอย่างเคร่งครัด และ \code{timingsOverlap} กำหนดให้วันตรงกันด้วย ช่วง 09:00 ถึง 12:00 กับ 12:00 ถึง 15:00 จึงไม่ทับซ้อน ระบบไม่เพิ่มเวลาพักหรือเวลาเตรียมห้องโดยอัตโนมัติ การอ่านวันที่จากแฟ้มต้นทางอธิบายในภาคผนวก \ref{app:dates}

\subsection{หน่วยค้นหา ช่องเวลา และกราฟข้อขัดแย้ง}
\code{scheduleProject} สร้างหน่วยสอบพร้อมกันจากความสัมพันธ์ของกฎ หรือใช้รายการสอบเดี่ยวเมื่อไม่เชื่อมกับวิชาอื่น น้ำหนักของหน่วยคือจำนวนรายการที่ต้องจัดและยังไม่มีเวลา ไม่ใช่จำนวนนักศึกษา จำนวนตอนเรียน หรือจำนวนแถวในแฟ้ม หน่วยที่มีรายการพร้อมเวลาอยู่แล้วถูกจำกัดให้ตรงกับเวลานั้น

ช่องเวลามาจากผลคูณของวันในช่วงสอบกับช่วงเวลารายวัน สำหรับการสอบเต็มวันใช้ช่วง fullDay จากนั้นกรองช่องที่ขัดกับข้อมูลคงที่ กลุ่มนักศึกษา ขอบเขตวัน และนโยบายปฏิทิน นโยบาย \code{never} ตัดวันออก ส่วนนโยบาย \code{only_if_necessary} ยังยอมให้ใช้ แต่คิดเป็นวันที่ควรหลีกเลี่ยง กราฟข้อขัดแย้งเชื่อมหน่วยที่มีกลุ่มนักศึกษาร่วมกันและมีช่องที่อาจทับซ้อน การแยกกราฟเป็นองค์ประกอบช่วยจำกัดการค้นหาเฉพาะส่วนที่เกี่ยวข้องกัน
ช่วงสอบรวมวันเริ่มและวันสิ้นสุด โดยไม่รับช่วงกลับด้านหรือยาวเกิน 366 วัน ช่วงเวลารายวันต้องถูกต้องอย่างน้อยหนึ่งช่วง แต่ไม่บังคับให้ต่างกันหรือไม่ทับซ้อน จึงตรวจข้อขัดแย้งจากช่วงนาทีจริง วันหยุดต้องระบุใน settings และไม่ได้ดึงจากปฏิทินราชการโดยอัตโนมัติ ค่าการตั้งค่าทั้งหมดอยู่ในภาคผนวก \ref{app:input}

\subsection{การเลือกหน่วยถัดไปและการเรียงช่องเวลา}
\code{solveUnits} ใช้ MRV เป็นเกณฑ์แรก โดยนับช่องที่ยังไม่ถูกบล็อกในสถานะปัจจุบัน เมื่อจำนวนเท่ากัน จึงเรียงน้ำหนักมากก่อน สอบเต็มวันก่อน จำนวนเพื่อนบ้านในกราฟมากก่อน จำนวนสมาชิกกลุ่มมากก่อน และดัชนีคงที่น้อยก่อน หน่วยถูกเรียงตาม ID ก่อนสร้างดัชนี จึงมีตัวตัดสินสุดท้ายที่ทำซ้ำได้

เมื่อความครอบคลุมเท่ากัน ระบบลดต้นทุนแบบเรียงลำดับความสำคัญสามองค์ประกอบ ได้แก่ จำนวนรายการในวันที่ควรหลีกเลี่ยง ภาระของกลุ่มนักศึกษา และความต้องการใช้ทรัพยากรพร้อมกันในช่วงเวลาเดียวกัน การเปรียบเทียบไม่ใช่การรวมทั้งสามเป็นคะแนนเดียว จึงไม่ยอมเพิ่มองค์ประกอบแรกเพียงเพื่อให้องค์ประกอบท้ายลดลงมาก กรอบปัญหา CSP และแนวคิด MRV ที่ใช้ในบทนี้อ้างอิงจาก Russell และ Norvig (2021) และโน้ตประกอบการสอนของ Carnegie Mellon University (n.d.) ส่วนต้นทุนแบบเรียงลำดับความสำคัญ สัมประสิทธิ์ และขอบเขตการพิสูจน์ใช้ implementation ของ \code{solveUnits} เป็นนิยามเฉพาะระบบ ไม่อ้างว่าตำรารับรองอัลกอริทึมนี้ทั้งหมด

ภาระที่เพิ่มจากการเลือกช่องคำนวณจากสมาชิกกลุ่มของรายการที่กำลังจัด โดยให้น้ำหนัก 10 ต่อรายการร่วมกลุ่มในวันเดียวกัน และ 3 ต่อรายการในวันปฏิทินก่อนหน้าหรือถัดไป น้ำหนักสองค่านี้เป็นพารามิเตอร์ที่กำหนดพฤติกรรม ไม่ใช่ค่าที่พิสูจน์ทางคณิตศาสตร์ เหตุผลของอัตราส่วนคือการที่การสอบร่วมวันเดียวกันกดดันนักศึกษามากกว่ากรณีคนละวันที่ติดกันหลายเท่า ผลของการเปลี่ยนค่าเหล่านี้วัดไว้ในบทที่ \ref{ch:perf} แล้วพบว่าอัตราส่วนที่ใกล้เคียงกันให้ผลแทบไม่ต่างกัน ส่วนองค์ประกอบที่สามนับจำนวนรายการ managed ที่เวลาทับซ้อนคูณน้ำหนักหน่วย เป็นตัวแทนของความต้องการใช้ห้องพร้อมช่วงเวลากันเท่านั้น ไม่ใช่การจัดห้องสอบหรือการพิจารณาความจุห้องจริง การลดค่านี้ช่วยลดโอกาสที่ตารางจะต้องใช้ห้องพร้อมกันจำนวนมากในช่วงเดียว เมื่อค่าต้นทุนเพิ่มเท่ากัน เรียงวันที่ เวลาเริ่ม และเวลาสิ้นสุดจากน้อยไปมาก
\subsection{งบการค้นหา การตัดกิ่ง และการปรับปรุง}
\needspace{10\baselineskip}แผนการค้นหาโดยสรุปมีดังนี้

สำหรับแต่ละองค์ประกอบของกราฟข้อขัดแย้ง: คำนวณขอบเขตบนของความครอบคลุม จากการจัดเรียงช่วงเวลาของแต่ละกลุ่มนักศึกษา ค้นหาความเป็นไปได้โดยเลือกหน่วยด้วย MRV ทีละตัว: ลองช่องเวลาตามต้นทุนจากน้อยไปมาก โดยเลือกวันปกติก่อนวันที่ควรหลีกเลี่ยง งดสำรวจสาขาที่ศักยภาพรวมต่ำกว่าคำตอบที่ดีที่สุดปัจจุบัน (ตัดกิ่งด้วยขอบเขตบน) พิจารณาสาขาที่ไม่วางหน่วยเมื่อการนั้นอาจเพิ่มความครอบคลุมรวม เมื่อสิ้นสุดการค้นหาความเป็นไปได้ ทดลองคำตอบตั้งต้นแบบ greedy อีกสามลำดับที่กำหนดแน่นอน ปรับปรุงภายในงบที่เหลือ ด้วยการซ่อมความครอบคลุม การย้ายหน่วย และการแลกที่อยู่สองหน่วย เก็บคำตอบที่ดีที่สุดตามน้ำหนักก่อน แล้วจึงต้นทุนตามลำดับความสำคัญ

งบค้นหาความเป็นไปได้เริ่มที่ค่ามากกว่าระหว่าง 1 กับจำนวนเต็มปัดลงของร้อยละ 60 ของ \code{searchBudget} และแบ่งระหว่างองค์ประกอบตามจำนวนตัวแปร สัดส่วนนี้เป็นพารามิเตอร์เช่นกัน การเปลี่ยนสัดส่วนไป 0.4 หรือ 0.8 ได้ผลชนิดเดียวกันตามที่วัดไว้ในบทที่ \ref{ch:perf} โดยเปลี่ยนเพียงการแบ่งงบระหว่างการค้นหากับการปรับปรุง ระบบพิจารณาวันที่ควรใช้ก่อน แล้วขยายไปยังวันที่ควรหลีกเลี่ยงเมื่อจำเป็น

การตัดกิ่งด้วยขอบเขตบนใช้ค่าที่ประเมินอย่างผ่อนปรนจากช่องเวลาและกลุ่มนักศึกษา หากสาขานั้นไม่อาจเพิ่มความครอบคลุมหรือปรับจำนวนรายการในวันที่หลีกเลี่ยงก็ไม่จำเป็นต้องสำรวจต่อ องค์ประกอบที่ถูกงบตัดไปแล้วจะไม่ถูกซ่อมให้ดูสมบูรณ์ในเบื้องหลัง

\code{visitedNodes} นับงานค้นหา ส่วน \code{improvementEvaluations} นับการประเมินปรับปรุง ผลรวมไม่เกินงบ แต่ไม่ครอบคลุมทุกคำสั่งประมวลผล เช่น การสร้างคำตอบตั้งต้นบางส่วน จึงไม่ควรแปลงตัวนับเหล่านี้เป็นเวลาหรือจำนวนการทำงานทั้งหมด

ขอบเขตบนคำนวณแยกตามองค์ประกอบของกราฟข้อขัดแย้ง เริ่มจากน้ำหนักรวมของทุกหน่วยในองค์ประกอบ แล้วหักส่วนที่ต้องเสียไปตามข้อจำกัดของแต่ละกลุ่มนักศึกษา สำหรับกลุ่มหนึ่ง รวบรวมช่องเวลาที่สมาชิกของกลุ่มใช้ได้ แล้วนับจำนวนช่องที่ไม่ทับซ้อนกันตามลำดับวันและเวลาสิ้นสุด จำนวนนี้คือความจุสูงสุดของกลุ่มนั้น หากกลุ่มมีหน่วยมากกว่าความจุ ส่วนเกินต้องหลุดออก โดยตัดน้ำหนักน้อยที่สุดออกก่อน ผลต่างที่เหลือคือความสูญเสียขั้นต่ำของกลุ่มนั้น ขอบเขตขององค์ประกอบจึงเท่ากับน้ำหนักรวมลบความสูญเสีย โดยการรวมค่าความสูญเสียของหลายกลุ่มเลือกเฉพาะกลุ่มนักศึกษาที่ไม่มีหน่วยสอบร่วมกัน เพื่อไม่ให้รายการสอบเดียวกันถูกนับเป็นความสูญเสียมากกว่าหนึ่งครั้ง

ขอบเขตนี้ไม่เคยต่ำกว่าคำตอบจริง เพราะทุกตารางที่เป็นไปได้ต้องวางสมาชิกของกลุ่มภายในช่องที่ใช้ได้ และช่องที่ทับซ้อนกันรองรับได้เพียงหนึ่งหน่วย จึงวางได้ไม่เกินความจุที่คำนวณแบบมองโลกในแง่ดีนี้ เมื่อคำตอบที่ค้นพบมีน้ำหนักเท่ากับขอบเขตบนของทุกองค์ประกอบรวมกัน จึงไม่มีคำตอบใดดีกว่าได้ และ \code{coverageOptimal} เป็นจริง สำหรับจำนวนรายการในวันที่ควรหลีกเลี่ยง ขอบเขตล่างคือผลต่างระหว่างขอบเขตบนรวมช่องทั้งหมดกับขอบเขตบนเฉพาะวันปกติ หากคำตอบที่ครอบคลุมถึงขอบเขตบนแล้วยังมีจำนวนรายการในวันดังกล่าวเท่ากับขอบเขตล่างนี้ \code{avoidedDaysOptimal} จึงเป็นจริงตามนิยามใน \code{src/lib/solver.ts}
\needspace{8\baselineskip}\subsection{ลำดับค้นหาและขอบเขตของข้อพิสูจน์}
\code{coverageOptimal} หมายถึงจำนวนที่จัดได้ถึงขอบเขตที่ใช้ได้ หรือค้นหาครบจนพิสูจน์ความครอบคลุมได้ ไม่ได้ยืนยันว่าภาระนักศึกษาต่ำที่สุดทุกด้าน \code{avoidedDaysOptimal} เพิ่มเงื่อนไขว่าจำนวนรายการในวันที่ควรหลีกเลี่ยงถึงขอบเขตล่างด้วย

\code{provablyImpossibleEvents} ระบุรายการเฉพาะที่จัดไม่ได้ภายใต้ข้อจำกัดที่พิสูจน์ได้ รายการเหล่านี้เป็นข้อเท็จจริงเกี่ยวกับข้อจำกัด ไม่ใช่ข้อสรุปว่าโครงการทั้งหมดไม่มีตารางที่เป็นไปได้ หากข้อมูลนำเข้าขัดกัน ส่วนที่ขัดกันอาจคงอยู่ในผลลัพธ์และทำให้ผลตรวจรวมเป็น invalid

\needspace{24\baselineskip}\subsection{ระดับความรุนแรงและสถานะ}
ข้อค้นพบมีระดับ \code{error} \code{warning} และ \code{info} พร้อมที่มา \code{source} \code{generated} \code{manual} หรือ \code{resource} สถานะรวมเป็น \code{invalid} เมื่อมี \code{error} อย่างน้อยหนึ่งรายการ หากไม่มี \code{error} แต่ยังมีข้อค้นพบ จะเป็น \code{valid_with_warnings} แม้ข้อค้นพบนั้นจะเป็น \code{info} เท่านั้น จึงควรอ่านสถานะร่วมกับรายการจริง

แต่ละกลุ่มตรวจมีสถานะ \code{passed} \code{failed} หรือ \code{not_checked} การพบข้อค้นพบที่อยู่ในกลุ่มทำให้กลุ่มนั้น \code{failed} ได้แม้เป็นคำเตือน ส่วนกลุ่มที่ไม่มีข้อมูลเพียงพอและไม่มีข้อค้นพบอาจเป็น \code{not_checked}

\code{SAME_TIME_CONTRADICTION} ปรากฏได้ทั้งในฐานะ issue ของตัวตรวจ และเหตุผลของหน่วยที่ตัวจัดตารางวางไม่ได้ การจำแนกจึงใช้บริบทของเขตข้อมูลร่วมกับตัวอักษรรหัส ไม่กำหนดว่ารหัสหนึ่งอยู่ในหมวดเดียวเสมอ เช่น \code{issueCodes} และ \code{solverUnscheduledReasons} อาจมีข้อความเดียวกัน แต่บอกข้อเท็จจริงคนละระดับ

ในชุดขัดแย้ง วิชาคู่เดียวมีกลางภาคและปลายภาค จึงเกิดเหตุผลสองหน่วยแต่มีรายการสอบไม่มีเวลาสี่รายการ หากรายงานนับสองเป็นจำนวนรายการสอบจะทำให้ขนาดผลกระทบลดลงครึ่งหนึ่ง เครื่องมือยืนยันผลจึงตรวจทั้งสองจำนวนแยกกัน
\needspace{20\baselineskip}\subsection{แนวทางใช้ผลตรวจ}
ผลตรวจควรนำไปแก้ต้นเหตุ ปัญหารูปแบบข้อมูลแก้ในแฟ้มต้นทาง ปัญหากฎแก้รายการอ้างอิงหรือความหมายของกฎ ส่วนงบค้นหาหมดต้องพิจารณาทั้งโครงสร้างข้อมูลและงบที่อนุญาต การเพิ่มงบอาจช่วยค้นหาต่อ แต่ไม่แก้รหัสวิชาผิดรูปแบบหรือข้อกำหนดที่ขัดกัน

รายงานไม่ถือว่าการผ่าน test suite ยืนยันทุกชุดข้อมูลจริง การทดสอบโปรแกรมเดิมกับการตรวจ fixture เป็นหลักฐานคนละบทบาท ดังที่แยกไว้ในบทที่ \ref{ch:method} ทั้งสองส่วนจึงต้องอ่านร่วมกันเมื่ออ้างผล

\subsection{ภาพหน้าจอเป็นหลักฐาน}
ภาพหน้าจอทั้งแปดภาพบันทึกจากสภาพแวดล้อมเดียวกัน คือเบราว์เซอร์ที่ล้างข้อมูลการจัดเก็บ ภาษาไทยเป็นค่าเริ่มต้น ขนาดหน้าจอ 1920x1080 และระดับซูม 100 เปอร์เซ็นต์ รายละเอียดการบันทึกทั้งหมด เช่น รุ่นเบราว์เซอร์ เวลา และแฮช SHA-256 ของแฟ้มภาพ อยู่ในแฟ้ม \code{docs/screenshots/screenshots.json} และสรุปไว้ในภาคผนวก C ภาพปกติทั้งหมดใช้ชุดข้อมูลหลัก ส่วนหน้าจอข้อควรตรวจสอบใช้ชุดกฎอ้างอิงล้าสมัยตามที่ระบุในคำบรรยายของภาพ ดังที่อธิบายไว้ในบทที่ 1 ภาพเหล่านี้บันทึกจากจุดอ้างอิงของวันที่ 5 กันยายน 2569 ซึ่งโค้ดการจัดตารางไม่ต่างจาก revision ปัจจุบัน การโต้ตอบที่ลึกกว่าการเปิดดูยังไม่ถูกทดสอบและอยู่ในงานต่อไป ส่วนชั้น cloud ตรวจบนระบบที่เผยแพร่จริงด้วยหลักฐานของตัวเองในหัวข้อถัดไป

ความถูกต้องของแหล่งข้อมูลที่ดึงกลับ & ไบต์ตรงกับที่อัปโหลดครบ 45 ไบต์ \\
การเพิกถอนลิงก์แชร์ & หลังเพิกถอน การอ่านได้รหัส 401 ส่วนลิงก์ที่เหลือยังใช้งานได้ \\
ความแยกไม่ได้ของข้อผิดพลาดการยืนยันตัวตน & เนื้อความ 401 เหมือนกันทั้ง id ที่ไม่รู้จักและความลับที่ผิด เช่นเดียวกับ 403 \\
ขอบเขตข้อมูลนำเข้า & แหล่งข้อมูลเกิน 20 รายการปฏิเสธ 413 ชื่อยาว 250 อักขระถูกตัดเหลือ 200 \\
การจำกัดอัตราการเขียน & ตอบ 429 ครั้งแรกเมื่อคำขอที่ 227 จาก 259 คำขอ ภายใน 19.5 วินาที \\\bottomrule
\end{longtable}}

การตรวจอัตราการเขียนต้องอ่านร่วมกับพฤติกรรมที่ Cloudflare ระบุไว้สำหรับตัวจำกัดชนิดนี้ คือทำงานแบบผ่อนปรนและเข้ากันได้ในท้ายที่สุด คำขอที่มาถึงพร้อมกันตรวจจากตัวนับที่เก็บไว้ในเครื่อง ทำให้การส่งคำขอเป็นชุดสั้น ๆ ทะลุเพดานได้ การตรวจจึงกดคำขอต่อเนื่องแทน และพบการปฏิเสธ 429 ครั้งแรกเมื่อคำขอที่ 227 รวม 32 ครั้งก่อนหยุดตามงบที่ตั้งไว้ ผลนี้ยืนยันว่าตัวจำกัดใช้งานจริงบนระบบที่เผยแพร่ แต่ไม่ใช่การควบคุมที่แม่นยำตรงเพดาน 120 คำขอต่อนาที

\subsection{วิธีวัดและสภาพแวดล้อม}
การวัดแบบ CLI เริ่มก่อนสร้างโปรเซสและสิ้นสุดเมื่อโปรเซสออกหลังเขียนผล จึงรวมการเริ่ม Node การอ่านแฟ้ม การนำเข้า การจัดตาราง การตรวจ และการเขียน JSON ไม่มีรอบอุ่นเครื่อง เพราะต้นทุนเริ่มโปรเซสเป็นส่วนของสิ่งที่ต้องการวัด

การวัดภายในโปรเซสนำเข้าแต่ละชุดครั้งเดียว เรียก \code{scheduleProject} หนึ่งครั้งโดยไม่วัด แล้ววัดอีกยี่สิบครั้ง ฟังก์ชันนี้รวมการทำสำเนา การสร้างรายการ การค้นหา คุณภาพ และการตรวจ จึงเรียกผลนี้ว่าเวลา scheduleProject ไม่ใช่เวลาของ solver ล้วน ทั้งสองชุดตัวเลขเกิดจาก \code{docs/data/bench.ts} แต่ละขนาดเก็บยี่สิบตัวอย่างต่อวิธีวัด รายงานค่ามัธยฐานพร้อมควอร์ไทล์ 1 และ 3 เพื่อแสดงการกระจายของค่ากึ่งกลาง 50 เปอร์เซ็นต์ ตัวอย่างดิบทุกค่าเก็บไว้ใน \code{benchmarks.json} การวัดครั้งนี้เกิดขึ้นบนเครื่องที่ยังมีแอปพลิเคชันเดสก์ท็อปอื่นทำงานอยู่เบื้องหลัง ผู้ทดลองไม่ได้เปิดงานอื่นโดยตั้งใจ แต่ระบบบันทึกโหลดเฉลี่ยขณะเริ่มวัดไว้ในตารางด้วย ค่าเวลาทั้งหมดจึงควรอ่านเป็นค่าที่รวมสภาพแวดล้อมของเครื่องในขณะนั้น ไม่ใช่ขอบเขตล่างสุดของระบบ

\subsection{งานต่อไป}
งานถัดไปด้านรายงานคือทดสอบการโต้ตอบที่ลึกขึ้นในเบราว์เซอร์ เช่น การแก้ตารางด้วยมือ และการจัดการข้อขัดแย้งของ revision ที่หน้าจอ โดยภาพแต่ละภาพควรระบุภาษา ขนาดหน้าจอ และแฮชข้อมูลควบคู่กันตามแบบแฟ้มหลักฐานปัจจุบัน
